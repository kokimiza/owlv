# 開発運用定義書

## 1. 物理・ネットワーク・仮想化アーキテクチャ

### 1.1 ネットワークトポロジーと境界防御

本システムは、外部インターネットおよび開発用ローカルマシンが属する不安全領域から、本番セグメント(internal_lan)を外部から完全に隔離する「ゾーン分離(セグメンテーション)設計」を基本とする。唯一の意図的な開口は、不安全領域から dev_lan の Git VM への `git push` のみであり、internal_lan へは構造的に到達できない。物理ホスト(OpenBSD)のパケットフィルタリング(`pf.conf`)により、仮想スイッチ間の通信は厳格に制御される。

```
【不安全領域(外部 / 開発環境)】
   [ 開発用ローカルマシン ]  ※コードの記述・レビューのみ。本番向けビルドは行わない
           │
           │ (ローカルLAN経由 / Forgejo への git push のみ許可)
           ▼
【物理ホスト: OpenBSD (本番オンプレミス)】
   │
   ├── [ 仮想スイッチ 1 (dev_lan) ]
   │       │
   │       ├── (10.0.2.10) [ Git VM: Forgejo ]
   │       │         │  push / tag をトリガに CI ジョブを発行
   │       │         ▼
   │       └── (10.0.2.20) [ Build VM: OpenBSD (本番と同一リリース) ]
   │                 │  Forgejo Runner (host モード) / GHC ネイティブビルド
   │                 │  成果物 + SHA256 を Git VM のレジストリへ格納
   │                 ▼
   ├── [ 仮想スイッチ 0 (internal_lan) ]
   │       │
   │       ├── (10.0.1.10) [ AP VM: Haskell / Brick (TUI) ]
   │       │       ▲
   │       │       │ (SCRAM-SHA-256 + TLS / RLS セッション変数)
   │       │       ▼
   │       └── (10.0.1.20) [ DB VM: PostgreSQL (RLS 有効) ]
   │
   └── [ 仮想スイッチ 2 (audit_lan) ]
           │
           └── (10.0.3.10) [ Audit VM: syslog 集約 / 改ざん検知 / 外部通報 ](§6)

   internal_lan(全VM)/ dev_lan(全VM) ──[UDP 514・一方通行のみ]──▶ audit_lan
   audit_lan ──[全ポート・全プロトコル・双方向]──✕ internal_lan / dev_lan (完全遮断)
   audit_lan ──[TCP 443・宛先 pf table 固定]──▶ 不安全領域(Twist / Discord / メールサーバーのみ)

【クライアント端末(運用者)】
   [ FDE + セキュアブート端末 ] + [ Yubikey (SSH PIV / タッチ必須) ]
           │
           └─── (AP VM ポート 8022 へ直接 SSH / TUI 転写)
```

#### 1.1.1 インナーエアギャップの開口方式(固定 IP の恒久ルール / 動的ピンホール)

通常時、仮想スイッチ 0(internal_lan)・仮想スイッチ 1(dev_lan)・仮想スイッチ 2(audit_lan)の相互間の通信は、ホスト OS の PF により「全パケットドロップ(双方向とも完全遮断)」とする。例外として開ける経路は宛先の性質によって以下の 3 種類に分かれる。

* **恒久的な狭域ルール(固定内部 IP 宛)**:AP VM → Git VM(デプロイ時のバイナリ取得、ポート 3000 限定)、およびホスト → Git VM(§4.2 のデプロイ承認ポーリング、同ポート)。宛先が固定内部 IP であるため時限化の必要がなく、`pf.conf` に常時許可として記述する。internal_lan 側から dev_lan への着信(webhook 等)は構造的に受け付けない — 承認状態の検知は常にホスト発のポーリングに限る。
* **動的ピンホール(DNS 解決に依存する外部宛)**:宛先が外部クラウドストレージである DR 射出(§2.2 の B2 / rsync.net)のみがこの形式を用いる。`owl-pfctl-pinhole` でホストがアウトバウンド通信を時限的に許可し、転送完了またはタイムアウトをトリガに即座に初期の完全分離状態へ復元する。
* **片方向の恒久許可(audit_lan 宛、§6.1)**:internal_lan・dev_lan の全 VM から audit_lan(Audit VM)への UDP 514(syslog)のみを常時許可する。逆方向(audit_lan → internal_lan / dev_lan)はポート・プロトコルを問わず例外なく遮断し、時限ピンホールの対象にも含めない。Audit VM の侵害は他segmentへの到達手段を一切生まない構造とする。

Build VM は dev_lan 内に常駐するが、internal_lan への経路は一切持たない。Build VM が侵害されても、成果物改ざんは manifest.txt の signify 署名検証(§4.2、署名鍵はホストが排他保持)で検出され、本番セグメントへの直接到達経路は存在しない(SHA256 単体は整合性確認にすぎず、成果物と SHA256 を両方書き換えられれば改ざん検知としては機能しない — 検出の核は署名検証である)。Audit VM も同様に audit_lan に隔離され、internal_lan / dev_lan への経路を構造的に持たない(§6.1)。

**送信元詐称対策の実装注記**:`pf` の自動 `antispoof` ディレクティブは、対象インターフェースに割り当てられたホスト自身の IP を基準に展開されるため、`vmd` の `tap(4)` 越しにゲストへ動的に割り当てられた IP(10.0.1.10 等)はホスト側に存在せず、自動展開では正しく機能しない(正当な通信まで誤ってドロップされる、または逆にガードされない)。各仮想スイッチ用インターフェースに対しては、ゲスト IP をマクロ化した手動ルール(`block in on $if_internal_lan; pass in on $if_internal_lan from $vm_ap_ip to any` 等)を `pf.conf` に明示記述し、`antispoof` キーワードに依存しない。

### 1.2 物理・認証レイヤー

* **クライアント端末**:OS レベルのフルディスク暗号化(FileVault / LUKS)およびセキュアブートを施した実用端末を標準とする。最高機密操作(鍵エスクローの取り扱い等)に限り、物理ストレージを排した TailsOS ブータブル USB 起動を要求する。
* **Yubikey PIV 認証**:SSH 秘密鍵は Yubikey のセキュアエレメント(PIV)内部に直接生成し、外部への取り出しを不可能とする。接続時は PIN 入力に加え、デバイスへの物理タッチを必須制約とする。
* **二段階緊縛**:AP VM の sshd は `AllowAgentForwarding no`、`AllowTcpForwarding no`、`PermitTunnel no` を強制し、AP VM が侵害された場合でもクライアント端末・他セグメントへのリバース経路を構造的に遮断する。各運用者アカウントには `ForceCommand` で TUI アプリケーションを強制し、シェルへの到達を禁止する。Brick の描画には PTY 割り当てが必須のため `PermitTTY yes` は明示的に維持し、「PTY は許可するがシェルには到達させない」という ForceCommand との組み合わせであることを `sshd_config` 上にも区別して記述する。

### 1.3 仮想化(ホスト)レイヤー

Linux カーネルを共有するコンテナ型仮想化は、コンテナエスケープのリスクを内包するため本番環境では採用しない。

* **vmd によるカプセル化**:OpenBSD 標準ハイパーバイザー `vmd` により、ハードウェアレベルで独立した 5 つの VM(AP / DB / Git / Build / Audit)を稼働させる。
* **メモリ・通信の完全分離**:各 VM は個別のメモリ空間を割り当てられ、仮想スイッチ(`internal_lan` / `dev_lan` / `audit_lan`)により L2 レイヤーからセグメントを分断する。`bridge(4)` はデフォルトでは同一スイッチ内のフレームをホストの `pf` を経由せず直接スイッチングする場合があるため、`net.link.bridge.pfil_member=1` および `net.link.bridge.pfil_bridge=1` を `/etc/sysctl.conf` で明示し、L2 トラフィックも必ず `pf` の評価を通過させる。internal_lan(AP/DB)・dev_lan(Git/Build)のように 1 スイッチに複数ゲストを収容するセグメントでは、この設定がない限り同一スイッチ内のゲスト間通信が `pf.conf` のルール記述と無関係に成立してしまう。
* **OS リリースのロックステップ運用**:Build VM と AP VM は**同一の OpenBSD リリース**(例: 7.7)で運用し、`sysupgrade` は必ず Build VM → ステージング検証 → AP VM の順で同期実施する。`uname -r` はリリース番号のみで `syspatch` の適用状態(パッチレベル)を含まないため、リリース一致だけでは ABI 差を排除できない。両 VM の `syspatch` 適用も同一タイミングでロックステップさせ、ビルド成果物のメタデータに `uname -r` と稼働中カーネル本体(`/bsd`)の SHA256 の両方を記録し、デプロイ時に AP VM 側と一致しない場合はデプロイを拒否する(§4.2)。`syspatch -l` は外部ミラーに問い合わせて未適用パッチを列挙するコマンドであり、エアギャップ環境でのロックステップ検証には使えない(ネットワーク非依存で算出できる `/bsd` のハッシュの方が確実)。
* **ECC メモリはホスト全体の物理要件**:`vmd` の全 VM は単一の物理ホストの RAM を共有するため、ECC メモリは VM 単位で選択できる属性ではなくホスト全体の前提条件である。PostgreSQL のデータ整合性(DB VM)が最大の動機だが、ECC の恩恵は AP/Git/Build/Audit の全 VM に等しく及ぶ。代替機調達時(§2.4)もホスト単位で ECC を必須とする。
* **VM ディスクイメージの配置先と容量前提**:各 VM の仮想ディスク(`ap.img` / `db.img` / `git.img` / `build.img`)はホスト OS 上の `/home/vmm/` に sparse ファイルとして置く(2026-06-22 以前は `/var/vmm/` に置いていたが、ホストの `/var` パーティションは固定 33.7G しかなく、4 台分の実消費(GHC ツールチェーン・cabal キャッシュ、Forgejo リポジトリ、PostgreSQL データの蓄積)を合算すると枯渇したため `/home`(ホストの自動パーティショニングで最大の空き領域を持つ)へ移設した)。`owl-config.toml` の `size =` は仮想ディスクの論理上限であり、ホスト側パーティションの実容量を保証しない。実際に `/var` 枯渇時、OS インストーラーがディスク書き込みに失敗してゲストカーネルがパニックし(`dump to dev ... not possible`)、`vmd` が `bsd.rd` への無限リブートループに陥る事象が発生した。再発防止として、`provision.sh` の `_require_free_space` がディスクイメージ作成前(STEP 5)および各 VM の OS インストール直前(STEP 7)にホスト側空き容量を検査し、不足時はゲストを起動させずに停止する。

### 1.4 インターフェースレイヤー(TUI 化)

HTTP 通信および Web ブラウザに付随する脆弱性クラス(XSS、CSRF、セッションハイジャック等)を構造的に排除するため、テキストベースユーザーインターフェース(TUI)を採用する。

* **Brick による描画**:画面描画は Haskell の TUI ライブラリ Brick で端末画面内に完結させる。運用者は AP VM(ポート 8022)へ直接 SSH 接続し、サーバー側でレンダリングされたエスケープシーケンスのみをターミナルに転写する。
* **残存攻撃面の認識**:本構成は Web 系脆弱性クラスを排除するが、攻撃面ゼロを意味しない。SSH プロトコルスタック、および端末エスケープシーケンス処理(エスケープインジェクション、例: OSC 52 を悪用したクリップボード汚染)は残存攻撃面として認識し、(a) DB 由来・外部由来の文字列を画面出力する際は制御文字をサニタイズする、(b) vty / Brick のセキュリティアドバイザリを CI の依存監査(§4.1)で追跡する、ことで緩和する。

### 1.5 データアクセス制御(RLS の結線)

DB VM の PostgreSQL は行レベルセキュリティ(RLS)を有効化するが、RLS はセッションが「誰であるか」を知らなければ機能しない。本システムでは SSH 認証で確立したユーザー同一性を、途切れなく DB セッションまで貫通させる。

```
[Yubikey PIV] → [sshd: 公開鍵認証] → [ForceCommand: TUI 起動 (環境変数 USER=...)]
      → [TUI: DB 接続確立 (SCRAM-SHA-256 + TLS)]
      → [SET app.current_user = '<ssh user>' をセッション初期化時に発行]
      → [RLS ポリシーが current_setting('app.current_user') を参照]
```

* **接続認証**:AP VM → DB VM の接続は `scram-sha-256` 認証 + TLS を必須とし、`pg_hba.conf` で接続元を 10.0.1.10 のみに限定する。
* **アプリケーションロールの最小権限**:TUI アプリの接続ロールは対象スキーマの DML のみを許可し、`BYPASSRLS`・スーパーユーザー権限を持たない。RLS ポリシーは `FORCE ROW LEVEL SECURITY` でテーブル所有者にも強制する。
* **監査ログとの統合**:すべての書き込みイベントには `app.current_user` 由来のユーザー ID を記録し、SSH ログイン(authlog)・アプリ監査ログ・DB 行履歴の三点で突合可能とする。
* **`SET` の適用範囲に関する前提**:現行構成は SSH セッション = TUI プロセス = 専用 DB 接続であり、コネクションプーラー(pgbouncer 等)を介さないため、セッション全体に効く `SET app.current_user` で安全に機能する。将来コネクションプーリングを導入する場合は、接続の再利用によりセッション変数が別ユーザーへ漏れる事故を防ぐため、`SET LOCAL` または `set_config('app.current_user', ..., true)` によるトランザクションスコープへの変更を必須とする。

## 2. データ保護・可用性・災害復旧(DR)戦略

### 2.1 バックアップデータの生成(三層構成)

WAL は差分ログであり、単体ではリストア不能である。本システムは以下の三層を DR 対象データとして定義する。

| 層 | 内容 | 取得頻度 | 目的 |
|----|------|---------|------|
| L1 | `pg_basebackup` による物理ベースバックアップ | 週次 | PITR の起点 |
| L2 | `archive_command` による継続 WAL アーカイブ | 常時(セグメント完結ごと) | 任意時点への巻き戻し(RPO 極小化) |
| L3 | `pg_dumpall` による論理ダンプ | 日次 | 物理破損・バージョン跨ぎ復旧の最終安全網 |

* DB VM の `postgresql.conf` にて `archive_mode = on` とし、`archive_command` は WAL セグメントを DB VM 内のアーカイブ領域へ書き出す。ホスト OS は深夜バッチ(§2.2)でこれを吸い出す。
* Git VM は `forgejo dump`(リポジトリ + DB + 設定の一括アーカイブ)を日次で生成し、同一パイプラインに載せる。
* リストア試験(§2.4)で三層すべての復元可能性を四半期ごとに実証する。**復元試験を経ていないバックアップはバックアップと見なさない。**

### 2.2 時限開口型暗号化クラウド DR

通常運用時、外向き通信は `pf.conf` により一切遮断する。深夜の指定時刻の数分間のみ、ホスト OS 上のオーケストレーター(`owl-control.sh`)が以下の不変パイプラインを実行する。

```
[DB: base backup + WAL + dump / Git: forgejo dump]
       │
       ▼ (内部吸い出し)
[ホスト RAM ディスク] ──> 【age 暗号化 (X25519 / ChaCha20-Poly1305)】──> [暗号化アーカイブ]
                                      ▲
                                      │ ホストは「受信者公開鍵」のみ保持
                                      │ (復号鍵はホスト上に存在しない)
[外部閉鎖(PF 全遮断)] ──> 【深夜数分間のみ開放】──> [rclone 同期]
                                                       ├──> [第一射出先: Backblaze B2]
                                                       └──> [第二射出先: rsync.net]
                                                       │
                                                       ▼
                                             【ステージング領域ゼロクリア → PF 完全閉鎖】
```

1. **データ集約と公開鍵暗号化**:DR 対象データをホスト RAM ディスクへ吸い出し、`age` の受信者公開鍵で暗号化する。**ホスト OS が保持するのは公開鍵のみ**であり、ホストが完全に侵害されても過去・将来のバックアップを復号する手段を攻撃者に与えない(Rev.1 の対称鍵 GPG 方式からの本質的改善点)。
2. **ピンホール開放**:`pfctl` により、射出先ストレージの特定エンドポイント(HTTPS: 443)へのアウトバウンドのみを一時許可する。
3. **二重射出**:`rclone` で暗号化済みアーカイブを **2 系統の独立した事業者**へ同期する。単一事業者のアカウント凍結・サービス障害・地理的災害への耐性を確保する。
4. **完全閉鎖とトラップ**:同期の成否にかかわらず、終了時に RAM ディスクをゼロクリアし、PF ルールを即座に完全遮断状態へ差し戻す。`trap` ハンドラにより、いかなる異常終了時でも開口状態が維持されることはない。
5. **完全性検証**:射出後、リモート側オブジェクトのチェックサムを照合し、結果を監査ログへ記録する。

### 2.3 復号鍵のエスクロー(本改訂の核心)

DR の成立条件は「暗号化アーカイブ」と「復号鍵」が**同時に失われないこと**である。age の identity(秘密鍵)は以下の規律で管理する。

* **生成**:identity はエアギャップ環境(TailsOS、ネットワーク未接続)で生成し、本番ホストには一度も置かない。生成端末上の痕跡は電源断で消滅させる。
* **保管(3 部複製・地理分散)**:
  1. **Yubikey 内**(`age-plugin-yubikey` により PIV スロットへ格納。タッチ + PIN 必須)— 日常的なリストア試験用
  2. **耐火金庫内のオフライン媒体**(紙への平文印字またはステンレス刻印 + 封緘)— 本番拠点とは別建屋
  3. **遠隔地の封緘保管**(信頼できる第三者または貸金庫)— 広域災害対策
* **検証**:四半期ごとのリストア試験(§2.4)で、エスクローされた identity による実復号を必ず含める。
* **ローテーション**:identity 漏洩の疑い、または保管者変更の際は新 identity を生成し、次回 DR 射出から新受信者公開鍵で暗号化する。旧アーカイブの世代管理期間が満了するまで旧 identity も保持する。

### 2.4 災害復旧(リストア)計画

物理マシン全損時の RTO 極小化のため、以下のベアメタルリストアを定義する。

1. **ハードウェア調達**:同等スペックの代替機(ECC メモリ、高耐久 NVMe SSD 必須)を調達。
2. **OS クリーンインストール**:OpenBSD(バックアップ時点と同一リリース)を最小構成でインストール。
3. **プロビジョニング自動化**:`owl-config.toml` を配置し、内製プロビジョニングスクリプトを実行。ホスト堅牢化、SSHD 緊縛、仮想スイッチ、4 VM の檻を数分で自動再構成する。
4. **復号鍵の投入**:エスクロー先(§2.3)から age identity を取り出し、リストア作業端末(TailsOS)へ投入する。
5. **データの復元**:射出先ストレージから最新アーカイブを取得・復号し、(a) ベースバックアップを展開、(b) WAL を `restore_command` でリプレイして目標時点まで前進(PITR)、(c) Git VM へ `forgejo dump` を復元する。論理ダンプ(L3)は物理復元が不能な場合の代替経路とする。
6. **再起動と検証**:`doas vmctl start -a` で全 VM を起動し、整合性チェックリスト(残高検算、最新仕訳の存在確認、Git HEAD ハッシュ照合)を通過させて復旧完了とする。

このリストア手順自体を四半期ごとに予備機で実走し、所要時間と手順書の乖離を記録・是正する。

## 3. ビルド環境と CI/CD パイプライン

### 3.1 OpenBSD ネイティブビルド(Rev.1 からの根本修正)

Rev.1 の「Alpine Linux コンテナによる musl 静的バイナリ生成」は、**OpenBSD が Linux ELF バイナリを実行できない**(Linux エミュレーションは OpenBSD 6.0 で削除済)ため成立しない。また、完全静的リンク(`-optl-static`)は libc の動的リンクを前提とした OpenBSD のセキュリティ機構と相容れない Linux 固有の発想であり、これも廃止する。

* **Build VM の新設**:dev_lan 上に本番 AP VM と同一リリースの OpenBSD を稼働させる Build VM(10.0.2.20)を設置し、ここを唯一の正規ビルド環境とする。GHC への高負荷を本番 AP VM から隔離する。
* **ツールチェーン**:GHC / cabal は OpenBSD ports(`lang/ghc`)から導入する。ports の GHC バージョンは上流より遅行するため、`tested-with` および `base` 等の下限制約は **ports 提供バージョンを正**として運用する(GHC 9.14 系が未着なら 9.6/9.8 系へ降格し、言語エディションは GHC2021 へ調整する)。ビルド環境のバージョン固定は `owl-config.toml` に宣言し、GitOps(§5)の管理下に置く。
  * OpenBSD の packages/amd64 は同一リリース内では基本的に更新されず、ツールチェーンのバージョンが変わるのは `sysupgrade`(または `-current` 追従)のタイミングに限られる。本システムは Build VM と AP VM を同一リリースへロックステップ運用する(本節冒頭・§1.3)ため、ツールチェーン更新は OS リリース更新と必ず同期する。それでも `vm-build/setup.sh` が `pkg_add ghc-<完全版番>` のように完全版番をインストール対象に固定すると、`sysupgrade` 後に旧版番の `.tgz` が削除されており `pkg_add` が `Can't find ghc-<版番>` で失敗する(実際に発生: `ghc-9.6` 指定 → `sysupgrade` 後の `ghc-9.10.1` で再発)。このため `setup.sh` は無印の `ghc` パッケージ(= そのリリースにおける現行版)をインストールし、実際にインストールされたバージョンが `owl-config.toml` の `toolchain.ghc_version`(GHC2024 要件を満たす下限値、現在 `9.10`)以上であることを事後検証する方式に変更した。バージョン文字列は pkg_add のターゲット指定ではなく、リリースごとに期待されるツールチェーンの下限を宣言・検証するためにのみ用いる。
* **リンク方針**:Haskell パッケージは GHC の既定どおり静的にバイナリへ取り込まれるため、動的依存は libc / libm / libpthread / gmp / libffi 等の基盤ライブラリに限られる。デプロイ単位は実質「単一バイナリ + OS リリース一致の保証」であり、Rev.1 が静的リンクで狙った運用簡素性は失われない。
* **開発ローカル環境の位置づけ**:開発者のローカルマシンは、コード記述・型検査・Core ユニットテストの高速イテレーション用とする。ローカル成果物は決して本番に持ち込まず、**本番候補バイナリは Build VM 産のみ**を正規とする(プラットフォーム差はコンパイル時に顕在化するため、push 前のローカル `cabal test` は引き続き有効)。

### 3.1.1 開発環境の定義(二環境モデル)

本システムの稼働環境は**開発**と**本番**の二種類のみとし、中間的な「ステージング」や「検証」環境区分は設けない。両者の差異は以下の通りである。

| 項目 | 開発環境 | 本番環境 |
|------|---------|---------|
| 実行基盤 | Docker Compose(ローカルマシン上) | OpenBSD VM(§1.1) |
| PostgreSQL | `db` コンテナ(単一ノード、TLS なし) | DB VM(RLS 有効 / SCRAM-SHA-256 + TLS / §1.5) |
| バイナリ出所 | ローカル `cabal build` / Docker `app` イメージ | Build VM 産(ホストの signify 署名 + SHA256 検証済み / §4.2) |
| 目的 | コード記述・動作確認・データ永続化の目視確認 | 実運用 |

**Docker Compose 運用規則**

* `docker compose up -d db` で PostgreSQL コンテナを先に起動し、ヘルスチェック(`pg_isready`)の通過を待つ。
* `docker compose run --rm app` で TUI を起動し、実際のデータ読み書きを手動で確認する。
* 接続先は Docker Compose ネットワーク内のサービス名 `db` であり、libpq 環境変数(`PGHOST=db` 等)は `docker-compose.yml` の `app` サービス定義に宣言されている。ハードコードは禁止する。
* 開発用 PostgreSQL パスワード(`owl-dev-only`)はリポジトリに平文で記載してよいが、**本番の認証情報は絶対に記載しない**。
* `docker compose build app` はソース変更後に明示的に実行する。古いイメージのまま動作確認する事故を防ぐため、ビルド省略を習慣としない。

### 3.2 テスト戦略(FCIS アーキテクチャに基づく役割分担)

本プロジェクトは FCIS(Functional Core, Imperative Shell)アーキテクチャを採用しており、テストの構造はこの境界に厳密に従う。

#### Core のユニットテスト(自動・CI で実行)

`Core/` は純粋関数のみで構成されるため、PostgreSQL・Docker・ネットワーク等のインフラを一切必要としない（FCIS は UseCases フォルダを設けず、orchestration は `Shell/` に置く。[CLAUDE.md](../CLAUDE.md) 参照）。

```
cabal test          # ローカルマシンで実行。全 Core ドメインロジックを網羅
```

* テスト対象:仕訳決定ロジック(`decide`)、状態遷移(`evolve`)、ECL 計算、固定資産会計、重要性判定など。
* 使用フレームワーク:Tasty / QuickCheck(プロパティテスト)/ HUnit(ケーステスト)。
* **インフラの有無でテスト構造が変わることはない**。これが FCIS の本質的な強みであり、cabal テストスイートに PG 接続テストを混入させてはならない。

#### Shell の動作確認(手動・開発環境で実施)

Shell 層(PostgreSQL イベントストア、effectful インタープリタ群、brick TUI)は副作用を持つため、自動テストの対象としない。

```
docker compose up -d db
docker compose run --rm app   # 実際に操作し、データ永続化・画面描画を目視確認
```

* 確認項目の例:仕訳入力 → PG への保存 → 再起動後のデータ復元、楽観ロック競合の実動作。
* この確認は開発者が手動で行うものであり、cabal のテストスイートには含めない。
* **Shell テストを cabal に追加しようとする場合は、FCIS 境界の侵犯として拒否する。**

#### Build VM での CI テスト(§4.1 で自動実行)

Forgejo Runner は push をトリガに `cabal test`(Core のみ)を Build VM 上で実行する。Shell の動作確認は開発者の責任とし、CI には含めない。

### 3.3 ブランチ戦略とタグ運用(構成管理)

幹ベース開発(Trunk-based Development)と不変セマンティックバージョニングを組み合わせる。

* **幹(`main`)への統合は PR 経由のみ**:開発者は短寿命なトピックブランチ(`feat/*`)で作業し、ローカル自動テスト通過後に PR を作成する。Forgejo のブランチ保護設定で `main` への直接 push を禁止し、最低 1 名の管理者によるレビュー承認(Approve)を必須とする。
* **レビュー承認 = デプロイ承認**:管理者は Forgejo Web UI(ポートフォワーディング経由のアクセスを前提とする)で PR の差分と Runner の CI チェック結果(§4.1 の Sec/Dev 両工程)を確認し、Approve する。本システムは二環境モデル(§3.1.1)を採用し中間検証環境を設けないため、承認済み PR の `main` へのマージそのものが本番デプロイの唯一の人間承認ゲートを兼ねる(§4.2)。Approve を却下(Request Changes)した場合はマージされず、デプロイも発生しない。
* **マージをトリガにした自動タグ付与**:承認済み PR が `main` へマージされると、Forgejo Runner が自動でリリースタグ(`vX.Y.Z`)を生成し本番候補ビルドを実行する。Git コミットハッシュ、成果物 SHA256、ビルド時の `uname -r`、GHC バージョンの組を構成管理台帳へ不変データとして記録する。

## 4. 自律型 DevSecOps とプル型デプロイメント

### 4.1 Forgejo Runner によるインラインセキュリティ・ビルド

Build VM 上の Forgejo Runner は **host モード**(コンテナ非依存)で稼働し、push / PR をトリガに以下を全自動実行する。①②は PR 作成時点(承認前)にも実行し、管理者が Approve 判断を下す材料として Web UI 上に結果を提示する。承認済み PR が `main` へマージされた際は、同じ①②をタグ付き本番候補ビルドとして再実行する。

#### ① 【Sec: 静的解析・脆弱性スキャン】(コンパイル前)

* **コード品質・静的バグ検知(HLint / Stan)**:型システムの死角となる実行時例外(部分関数等)や不適切な遅延評価を静的に検知・遮断する。
* **依存関係セキュリティ監査**:cabal の freeze ファイルを走査し、依存ライブラリの既知脆弱性を検査する。照合先は Haskell Security Advisory DB(`hsec` 系ツール)および OSV データセットとする。
* **エアギャップ型脆弱性同期(Gated Sync)**:脆弱性 DB の更新を本番側から外部へ取りに行くことは一切しない。外部 DMZ の中継サーバーが日次で公式フィード(OSV / NVD / Haskell SecAdv)をダウンロードし、TAR 化のうえ署名(`signify` を第一選択とし、OpenBSD ネイティブの検証経路を用いる)を付与する。深夜 DR 射出(§2.2)と逆方向の同期フェーズとして、ホスト OS が署名済みアーカイブをプルし、検証合格分のみを Git VM へ流し込む。

#### ② 【Dev: 再現可能なクリーンビルド】(コンパイル時)

* **ビルドキャッシュの世代管理**:Build VM 内の `~/.cabal` / `dist-newstyle` をジョブ間で安全に共有・世代管理し、フルビルド時間の長大化を防ぐ。キャッシュ汚染を疑う場合は GA ビルドに限りキャッシュレスで再現ビルドを行い、ハッシュ一致を確認する。
* **改ざん防止ハッシュの自動埋め込み**:成功した成果物に対し即座に `sha256sum` を実行して固有ハッシュ(`owlv-app.sha256`)を生成し、Forgejo リリースノートおよび Git メタデータへ自動書き込みする。

### 4.2 プル型(Pull-based)エアギャップ・デプロイ

開発側から本番へ送り込むプッシュ型デプロイは、開発端末侵害時のバックドアとなるため全面禁止とする。デプロイは本番側が引き抜くプル型を徹底する。

```
[管理者: Forgejo Web UI で PR を Approve & Merge]
                  │ (main への merge イベント)
                  ▼
[Forgejo Runner (Build VM)] ──> 自動タグ付与・ビルド・テスト ──> 成果物 + manifest.txt
                                 (タグ/コミット/uname -r/各バイナリ SHA256) を
                                 Git VM 内レジストリへ未署名のまま隔離配置
                                                     │
                                                     ▼ (恒久ルール、ホスト → Git VM)
                  [ホスト: owl-control.sh sign-poll] ──> 未署名 manifest.txt を検知し
                                 ホスト保管の signify 秘密鍵で署名、Git VM へ書き戻し。
                                 リリースを draft=false で公開(= 「承認済み・未デプロイ」)
                                                     │
                                                     ▼ (恒久ルール、§1.1.1)
[ホスト: owl-control.sh deploy-poll] ──> 【Forgejo API への定期ポーリング(5分間隔)】
       │ 未デプロイのリリースを検知
       ▼
[AP VM へ SSH 経由でデプロイ指示] ──> [AP VM が Git VM から自発的プル (HTTP)]
       │
       ▼
【三重検証】 manifest.txt の signify 署名検証 / OS リリース一致 (uname -r) /
            各バイナリの SHA256 一致(manifest.txt 記載値との比較)
       │
       ▼
【アトミック入れ替え(シンボリックリンク切替)】──> 失敗時は旧リンクへ 1 秒で復帰
       │
       ▼
【ホストが Forgejo API へ「デプロイ済み」を書き戻し(audit trail)】
```

1. **人間承認**:管理者がポートフォワーディング経由で Forgejo Web UI に接続し、PR の差分と Runner の CI チェック結果を確認した上で Approve する。ブランチ保護(最低 1 approval 必須)により、未承認コードは `main` へ統合されない。これがデプロイの唯一の人間承認ゲートであり、Request Changes による却下も可能(§3.3)。
2. **成果物のステージング(未署名)**:承認済み PR の `main` へのマージをトリガに Runner が自動でタグ付与・ビルド・テストを実行し、生成した正規バイナリとハッシュを Git VM 内の隔離レジストリへ**未署名のまま**配置する。`signify` 秘密鍵は Build VM 上に置かない — Build VM は dev_lan 上に常駐し Forgejo Runner という外部入力(push/PR)を直接処理する VM であり、ここに署名鍵を置くと Build VM 侵害時に攻撃者が改ざんバイナリへ正規の署名を付与できてしまい、§4.2 全体の「成果物改ざんは署名検証で検出される」という前提(信頼の根)が崩壊する。署名は鍵を保持するホスト OS が後段(3)で行う。
3. **ホスト署名(信頼の根の一元化)**:`owl-control.sh sign-poll` が5分間隔のホスト発ポーリングで Git VM 内の draft=true(未署名)のリリースを検知し、ホスト OS が排他的に保持する `signify` 秘密鍵で `manifest.txt` に署名し、`manifest.txt.sig` を Git VM へ書き戻した上でリリースを draft=false に切り替える。`sign-poll` は無人実行の cron ジョブであり毎回人手を介さないため、age identity(§2.3)のような物理エアギャップ生成・都度の人手投入は前提にできない — 鍵は `provision.sh` 実行時にホスト上で生成し(`host/steps/01-host-foundation.sh`)、`/etc/owlv/release-signify.sec` にホストのみが読める権限で常駐させる。これにより署名鍵は Build VM(外部入力である push/PR を直接処理し攻撃面が最も広い VM)から完全に排除され、Build VM 単体の侵害では正規の署名を持つ改ざんバイナリを作れない。公開鍵 `/etc/owlv/release-signify.pub` は AP VM へ手動配置する。
4. **ホスト駆動のプルデプロイ**:`owl-control.sh deploy-poll` が 5 分間隔で Forgejo API を照会し(internal_lan 側からの着信は受け付けず、検知は常にホスト発のポーリングに限る)、ローカルの既デプロイ台帳(`/etc/owlv/deployed_tags`)に無いタグを検知すると、AP VM へ SSH 経由でデプロイを指示する。AP VM から Git VM への実際のダウンロードは §1.1.1 の恒久ルールを経由する(時限ピンホールは使わない)。
5. **三重検証とアトミック入れ替え**:AP VM が `manifest.txt` / `manifest.txt.sig` / 各バイナリをダウンロードし、(a) `signify -V` で `/etc/owlv/release-signify.pub`(ホストが生成した署名鍵の公開鍵、事前に手動配置)による署名検証、(b) `manifest.txt` 記載の `uname_r` および稼働中カーネル(`/bsd`)の SHA256(§1.3 の syspatch ロックステップ検証)と AP VM 自身の現在値の一致、(c) 各バイナリの SHA256 が `manifest.txt` 記載値と完全一致することを検証する。3 つすべて合格した場合のみ `/usr/local/bin/owlv-app_vX.Y.Z` のようにバージョン固有名で配置し、シンボリックリンクをアトミックに切り替える。`owlv-projector`(常駐デーモン)は切替後に再起動・起動確認を行い、失敗時は旧リンクへ即時ロールバックして復帰する。
6. **完了記録**:デプロイ成功後、ホストが既デプロイ台帳に追記し、Forgejo API へ当該リリースを「デプロイ済み」として書き戻す(リリース名にタイムスタンプを付与)。これにより同一リリースの再デプロイを防ぎ、承認(Approve)からデプロイ完了までの全工程が Forgejo 上の不変ログとして追跡可能になる。

### 4.3 GitOps によるインフラのコード化(IaC)

構成ドリフトを防ぐため、アプリケーションコードのみならずインフラ構成のすべてを Git リポジトリで一元管理する。

* **宣言的記述**:`pf.conf`、`vmd.conf`、各 VM のプロビジョニングスクリプト、`postgresql.conf` / `pg_hba.conf`、RLS ポリシー定義(DDL)、Build VM のツールチェーン固定(`owl-config.toml`)をすべてコード化し、バージョン管理下に置く。
* **不変運用の厳守**:本番への設定変更は実機を直接触らず、必ず Git 上の構成ファイル変更 → Forgejo 検証パイプライン → 適用、の経路のみを許可する。インフラ全体を「コードから 100% 同一状態で再生成可能」に保つ。

## 5. ホスト OS の堅牢化

本アーキテクチャにおいて、PF・vmd・DR 暗号化・ピンホール制御・デプロイ承認のすべてを掌握するホスト OS は**単一の信頼の根**であり、ホスト侵害は全系崩壊を意味する。VM の檻の強度はホストの無欠性に依存することを明示的に認め、以下を恒常統制とする。

* **管理経路の極小化**:ホストへの SSH は原則無効とし、管理は物理コンソール(またはシリアルコンソール)からのみ行う。やむを得ず SSH を許可する場合も、専用管理 VLAN + Yubikey 公開鍵限定 + `ForceCommand` による操作メニュー強制とする。
* **OS 標準防御の全面活用**:`syspatch` の即日適用、`pledge` / `unveil` を備えた base ツールの優先利用、不要デーモンの全停止、`securelevel` の引き上げを基本とする。内製スクリプト(`owl-control.sh` 等)は可能な限り base ユーティリティのみで構成し、ports 依存を最小化する。
* **`syspatch` 適用時の VM 起動順序**:カーネル更新を含む `syspatch` はホスト OS の再起動を要し、ホスト再起動は稼働中の全 VM(AP / DB / Git / Build / Audit)を強制停止させる。シャットダウン順序は依存関係の逆順(AP → DB、Git/Build は独立して停止可、Audit は他から独立のため任意のタイミングで停止可)とし、`/etc/rc.shutdown` に `vmctl stop` の順序を明示する。再起動後は DB VM → AP VM → Git/Build VM → Audit VM の順に `vmctl start` し、AP VM 起動前に DB VM の `pg_isready` 通過を待つ。この起動順序を経ない `vmctl start -a` の単純並列起動は、AP VM が DB 未起動状態で接続を試みてエラーログを出すため避ける。
* **改ざん検知**:ホストの構成ファイル群(`/etc` 以下および内製スクリプト)のハッシュツリーを日次で取得し、Git 管理下の期待値(§4.3)と照合する。乖離検出時は DR 射出・デプロイを含む全自動処理を停止し、人間の確認を要求する。
* **監査ログの外部化**:ホストおよび各 VM の syslog は DB VM とは独立したログ集約点(Audit VM、§6)へ転送し、深夜 DR パイプラインで暗号化アーカイブに同梱する。侵害後のフォレンジック可能性を確保する。

## 6. 監査基盤(Audit VM)による特権侵害の検知と隔離

§5 で述べた「独立したログ集約点」を Audit VM(10.0.3.10、`audit_lan` 仮想スイッチ上)として具体化する。本番環境(AP/DB)・開発環境(Git/Build)いずれかの特権(root)が奪取された場合でも、それを検知し外部へ即時通報する一方、Audit VM 自身がデータ流出の踏み台になることをホスト OS の `pf` でネットワークレイヤーから構造的に排除する。

### 6.1 ネットワーク隔離の鉄則(ホスト `pf` で強制)

既存の `internal_lan`(10.0.1.0/24)・`dev_lan`(10.0.2.0/24)に加え、`vmd` 上に第三の仮想スイッチ `audit_lan`(10.0.3.0/24)を新設し、Audit VM(10.0.3.10)のみを収容する。§1.1.1 と同様、スイッチ間通信はホスト OS の `pf` で「既定全遮断 + 最小限の明示許可」を徹底する。

* **鉄則①(一方通行)**:既存 4 VM(10.0.1.0/24・10.0.2.0/24)から Audit VM への syslog 転送のみを許可し、Audit VM から他segmentへの通信は全ポート・全プロトコルで双方向遮断する。送信元 IP 詐称対策は §1.1.1 末尾の注記のとおり、`antispoof` の自動展開ではなく VM ごとの IP を明示した手動ルールで行う。**プロトコルとして UDP/514 を選ぶ理由**:syslog を TCP(または RFC 5425 の syslog over TLS)化すると、コネクション確立のハンドシェイク(SYN-ACK)で Audit VM 自身が internal_lan / dev_lan 宛にパケットを送る必要が生じ、「audit_lan から他segmentへの通信は全ポート・全プロトコルで双方向遮断」というパケットレベルの絶対則と矛盾する。UDP の一方向・応答なしという性質こそが、この鉄則をアプリケーション層の意図だけでなくパケットレベルでも成立させる前提条件である。これにより失われる完全性・順序保証・送達保証は、§6.3 のログ受信時点でのハッシュチェーン記録によって事後的に補う(欠落自体の検出はできるが、欠落したログ内容そのものの復元は保証しない)。
* **鉄則②(メタ情報のみ・ドメインデータ排除)**:AP/DB/Git/Build VM および ホスト自身から Audit VM へ送るログは、仕訳金額・顧客名等のドメインデータを一切含めず、「特権昇格(su/sudo)」「pf.conf 変更」「SSH ログイン」の成否メタログに限定する。マスキングは送信元(各 VM・ホストの `syslog.conf`)で行い、Audit VM 側でのマスキングには依存しない(到達した時点で既に機密データが存在しない状態を保証する)。実装上は各 VM・ホストの `syslog.conf` に `auth.* @<Audit VM IP>` の一行を追加するだけでこの限定が成立する — OpenBSD の `auth` ファシリティには元々 `su`/`sudo`・`sshd` のログイン成否・(ホストでは)`owl-integrity-check.sh` の改ざん検知アラート(`auth.warning`)しか流れず、owlv アプリのドメインログは別ファシリティを使うため転送対象に混入しない。これにより蓄積されるのは「攻撃の履歴」のみとなり、§1.5 の SSH authlog・アプリ監査ログ・DB 行履歴の三点突合と同一のメタデータ系列を補完する。
* **鉄則③(送信先ホワイトリスト固定)**:Audit VM はアラート通知のため外向き 443(HTTPS)を開けるが、`pf` 単体は L3/L4 のみを判定するためドメイン名を直接指定するルールは存在しない。Audit VM 上での DNS 動的解決をそのまま `pf` の `table` へ反映する方式は採用しない — Audit VM が問い合わせる DNS リゾルバ自体が侵害・キャッシュポイズニングされた場合、攻撃者の任意の IP がテーブルに書き込まれ、データ外出し経路が動的に開いてしまう。代わりに、通知先事業者(Slack / Discord / 指定メールサーバー)が公開している公式 IP レンジ(CIDR)を `pf.conf` の `table <notify_dst> { ... }` へ**静的にハードコード**し、`pf.conf` の GitOps 管理(§4.3)下で事業者側のレンジ変更時のみ人手で更新する。Audit VM からの DNS クエリ自体も発生させないため、DNS 経路を攻撃面として持たない。インターネット全体への自由な通信は構造的に発生しない。

### 6.2 検知トリガと通報経路

Audit VM 上の監視プロセスは受信ログをリアルタイムにパターンマッチし、以下のいずれかを検出した場合に直ちに鉄則③の経路でアラートを発報する:sudo/su の失敗連続、未承認 IP からの SSH ログイン成功、`pf.conf` ハッシュの§5 期待値からの乖離。検知から通報までを単一プロセス内で完結させ、外部キューや中間サーバーを経由しない(中間段がそれ自体踏み台になることを避ける)。

### 6.3 Audit VM 自体の要塞化

* **`schg` フラグによる `pf` の固定**:Audit VM 内の `/etc/pf.conf` に `chflags schg` を付与し、カーネルセキュアレベルを 1 以上に設定する。これにより root を奪われても Audit VM 自身のファイアウォール定義の書き換えはカーネルレベルで拒否される。
* **`newsyslog` と不変フラグの整合**:稼働中のログファイルには `schg` / `sappnd` を付与しない。OpenBSD では `schg` も `sappnd` も root 権限下でも `mv` / truncate を一切受け付けないため、これらを稼働中ファイルに付けると `newsyslog` のローテーション(リネーム → 新規作成)自体がカーネルレベルで失敗し、ログ肥大化とディスク枯渇を招く。代わりに `newsyslog.conf` を素のローテーション設定で稼働させ(この設定ファイルのみ `schg` で固定する)、ローテーション完了後に確定した過去ログ(`audit.log.0.gz` 等)に対して、ローテーション直後の cron ジョブが `chflags sappnd`(追記済み確定ログとしての改変防止)を付与する。アクティブなログファイルが書き込み中に改変されるリスクは、§6.2 の検知プロセスがログを受信した時点で別途ハッシュチェーンに記録することで補う。
* **運用上の制約**:securelevel ≥ 1 適用後、`/etc/pf.conf` の `schg` 解除は単一ユーザーモードでの再起動を要する。Audit VM の正規の設定変更(GitOps、§4.3)は「再起動を伴うメンテナンス手順」として明示し、稼働中のホットパッチは構造的に不可能であることを前提に運用する。
* **`newsyslog` による自動巡回**:標準の `newsyslog` が受信したリモートログを日次で `gzip` 圧縮し、過去 30 日分をローリング保持する。確定済みログ群のハッシュチェーンは Audit VM 内に閉じた記録として保持する — 鉄則①によりホストから Audit VM へ到達する経路は構造的に存在しない(host/conf/pf.conf は Audit VM 宛の一方通行 UDP 514 のみを許可し、ホスト発の能動的な問い合わせ経路は無い)ため、ホスト側からの遠隔突合は行わない。侵害後のフォレンジックは物理コンソールから Audit VM に直接アクセスして行う。
