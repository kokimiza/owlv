# OpenBSD / vmd 選定根拠書

> **前提**: `vmd` は OpenBSD 専用のハイパーバイザーソフトウェアではない。`vmd` 自体は他 OS をゲストとして動かせる汎用ハイパーバイザーであり、「ホスト OS = OpenBSD」「ハイパーバイザー = vmd」「全ゲスト OS = OpenBSD」は **3 つの独立した意思決定** である。本書はこの 3 点を分離して論じ、なぜ QEMU/KVM・Xen・bhyve 等ではなく vmd を、なぜ異種混在(例: Build VM だけ Linux)ではなく全 VM を OpenBSD で統一したのかの合理性を示す。関連: [dev_sec_ops.md §1.3](dev_sec_ops.md) 仮想化(ホスト)レイヤー。

## 1. ハイパーバイザー選定: なぜ vmd か

候補は実質的に 4 つだった: `vmd`(OpenBSD)、QEMU/KVM(Linux)、Xen、bhyve(FreeBSD)。

### 1.1 攻撃面: デバイスエミュレーションの最小性

ハイパーバイザーのゲスト脱出(VM escape)は、ほぼ例外なく **デバイスエミュレーション層** から発生する。QEMU は歴史的に VGA、USB、フロッピーコントローラ、サウンドカード等、レガシーデバイスを多数エミュレートしており、CVE-2015-3456(VENOM、フロッピーコントローラのバッファオーバーフローによるホスト脱出)はその典型例である。エミュレートするデバイス数とコード行数が、そのまま脱出可能な攻撃面の広さになる。

`vmd` はこれと対照的に、OpenBSD カーネルのハイパーバイザーモジュールである `vmm(4)` と協調し、自身が担当するユーザーランドのエミュレーション層を `vioblk` / `vionet` / `virtio-console` / `vmmci`(VM 管理用シグナリング)の **virtio 系最小セットのみ** に絞っている。CPU 仮想化支援(VT-x/SVM)やメモリ管理(EPT/RVI)はカーネル内の `vmm(4)` が担い、`vmd(8)` はその制御とデバイスエミュレーションに専念する役割分担になっている。レガシーデバイス・GPU・USB パススルー等は一切実装しない。これは機能不足ではなく、OpenBSD の設計哲学である「複雑性は脆弱性の温床」を仮想化レイヤーにも適用した結果である。本システムの VM は GUI も周辺機器も必要としない(§1.4 TUI 化により HTTP/GUI 攻撃面を排除する設計と一貫している)ため、この機能制限はコストではなくメリットになる。

### 1.2 信頼境界とパッチ供給網

`vmd` は OpenBSD base に同梱され、`syspatch` の対象に含まれる。つまりハイパーバイザーは **OpenBSD のリリースサイクルと一体で保守される**。これは「CVE フィードを別個に追跡しなくてよい」ことを意味しない(`vmd` 関連の問題も他の base コンポーネントと同様に公開・修正される)が、ホスト OS とハイパーバイザーで別々のパッチ供給網・別々のリリースサイクルを並行監視する必要がなく、**監視対象が一元化される**という意味で運用上のメリットがある。

QEMU/KVM を採用する場合、ホストが OpenBSD である本構成では選択し得ない(KVM は Linux カーネル機能であり、ホスト OS を Linux に変更する必要がある)。Xen も Dom0 として Linux または専用カーネルを要求し、構成要素が増える分だけ TCB(Trusted Computing Base)と監査対象が拡大する。bhyve は FreeBSD 専用であり、ホストを OpenBSD から FreeBSD に変更しない限り採用できない。いずれも「ホストは OpenBSD」という前提(§1.3)と衝突するか、追加の異種 OS・パッケージ管理・パッチサイクルを持ち込む。

### 1.3 ホスト OS との統合度

`vmd` は `vm.conf` / `vmctl` という OpenBSD ネイティブの設定・運用 IF を持ち、仮想スイッチは `bridge(4)` という base 同梱の機能で構成できる。Open vSwitch のような追加のソフトウェアスタックは不要であり、`pf.conf` から仮想スイッチ単位でフィルタリングできる(本書 §1.1 のエアギャップ設計はこの一体性に依存している)。`doas` による権限分離、`rcctl` によるサービス監督、`login.conf` によるリソース制限も `vmd` プロセスにそのまま適用される。libvirt は API 統一・複数ハイパーバイザー対応・自動化を目的とした成熟したツールであり、それ自体に問題はない。しかし本システムは単一ホスト・単一ハイパーバイザー(`vmd` のみ)・固定構成であり、libvirt が提供する抽象化の恩恵(マルチハイパーバイザー対応や大規模自動化)を活用する場面がない。そのため **本設計では libvirt を採用せず**、`vm.conf`/`vmctl` を直接運用する構成とした。

### 1.4 品質保証プロセスの一体性

`vmd` は OpenBSD プロジェクト自身が開発・レビュー・リリース・回帰テストを行う base コンポーネントであり、OS 本体の品質保証プロセスにそのまま含まれる。これは QEMU のように「外部の独立したコンポーネントを OS に組み合わせて使う」構成とは性質が異なる。パッチが OpenBSD のコードレビュー体制・リリースサイクルを経て base 全体と同じ経路で配布されることは、外部依存を個別に評価・追跡する必要がある構成と比べて、サプライチェーン上の信頼境界を単純化する。

### 1.5 制約の明示(誠実な評価)

`vmd` は QEMU/KVM や Xen に比べて機能面で明確に劣る。ライブマイグレーション、スナップショット、GPU パススルー、UEFI を要求する多様なゲスト OS のサポートはいずれも持たない。本システムは単一物理ホスト上の固定 4 VM 構成であり、これらの機能を必要としていないため実害はないが、将来 GPU 推論や複数物理ホスト間の VM 移動が要件化した場合は、この選定を見直す必要がある。これは隠すべき欠点ではなく、選定時に許容したトレードオフとして明記する。

## 2. ゲスト OS 選定: なぜ全 VM を OpenBSD にするか

`vmd` は OpenBSD 専用ではなく、virtio ドライバを持つ他 OS(Linux 等)もゲストとして起動できる。したがって「Build VM だけ Linux にして Docker を使う」といった異種混在構成も技術的には可能だった。それでも全 VM を OpenBSD に統一したのは、以下の理由による。

### 2.1 ビルド・実行環境の完全一致(ロックステップ運用)

Haskell/GHC は静的リンク・動的リンクのどちらも選択可能であり、「動的リンクが前提」というわけではない。問題は、ビルド環境と実行環境の libc・ABI・カーネル ABI が異なる場合、**ビルド済みバイナリの互換性が保証できない**ことにある(動的リンクであれば共有ライブラリのバージョン差異が直接問題になり、静的リンクであっても syscall ABI やカーネル機能への依存が残る)。dev_sec_ops.md §1.3 が定める「Build VM と AP VM は同一の OpenBSD リリースで運用し、`uname -r` が一致しない場合はデプロイを拒否する」というロックステップ運用は、この互換性問題を「ビルド環境 = 実行環境」という不変条件で構造的に解消するものであり、Build VM と AP VM が **同一 OS・同一リリース** であることを前提にしている。

異種 OS(例: Build VM = Ubuntu + musl 静的リンク)を選んだ場合、この互換性問題は「コンテナイメージのベース OS を固定する」「静的リンクで ABI 依存を切る」といった別の仕組みで代替可能ではある。しかし、その代替手段の本質は **Linux コンテナが Linux カーネルを共有する**ことに依存しており、本システムが §1.3 で採用しないと定めた前提(コンテナ型仮想化はカーネル共有によるエスケープリスクを内包する)と矛盾する。Build 環境と実行環境を VM レベル・OS レベルで一致させることで、追加の抽象化層(コンテナランタイム・静的リンクの ABI 切り離し)を挟まずに「ビルドした環境で動かす」を保証できる、というのが本システムの選択である。さらに、base/ports のファイルシステム・レイアウトや共有ライブラリの探索パスも完全に一致するため、Linux ディストリビューション間で発生しがちな `/usr/lib64` と `/usr/lib/x86_64-linux-gnu` のようなマルチアーキテクチャ・パスの差異による実行時リンクエラーの余地が構造的に排除される。

### 2.2 運用知識・監査対象の単一化

ホスト・AP VM・DB VM・Git VM・Build VM のすべてが OpenBSD であることにより、運用者が習熟・監査すべき対象は次のように単一化される。

| 観点 | 統一した場合 | 異種混在の場合 |
|---|---|---|
| パッチ適用 | `syspatch` 一本化 | OS ごとに異なるツール・サイクル(apt/yum/syspatch 等)を個別追跡 |
| パケットフィルタ | `pf.conf` の文法・運用知識のみ | `pf` + `iptables`/`nftables` 等を併用。特に Linux 側でコンテナランタイムを採用した場合、iptables ルールが動的に自動生成・書き換えられ運用者の目に見えにくくなるため、整合性検証とルール監査の難易度が増す |
| 権限分離モデル | `doas` + `pledge`/`unveil` 前提の単一モデル | `sudo`/`doas`/`setuid` 等が混在し脅威モデルが分裂 |
| サービス監督 | `rcctl` 一本化 | `rc.d`/`systemd`/`init.d` 等が混在 |
| ペネトレーションテスト範囲 | 単一 OS の既知攻撃面を深く検証 | OS ごとに攻撃面が異なり、テスト範囲が線形に増加(pentest_spec.md の検証コストにも直結) |

本システムは単独運用者(または小人数)を前提とした個人インフラであり、「複数 OS のセキュリティモデルを並行して把握し続けるコスト」は実質的に監査漏れのリスクに直結する。OS を 1 種類に絞ることは、機能的な制約ではなく、**有限な運用者の注意力という資源を最も脆弱性の少ない 1 点に集中投資する**という設計判断である。

### 2.3 セキュアバイデフォルトの一貫適用

OpenBSD は W^X(Write XOR Execute)を原則として全プロセスに適用し、例外を極力排除する設計方針を取る。ASLR、`pledge(2)`/`unveil(2)` によるシステムコール制限・ファイルシステム可視性制限も base の標準機能として提供される。汎用 Linux ディストリビューションは、一般に OpenBSD base より大きなユーザーランド(systemd・D-Bus・polkit 等の特権デーモン群を含むことが多い)を持つ。これはいずれかの VM に汎用 Linux ディストリビューションを採用した場合、その VM だけ構成要素・運用モデル・攻撃面の質が他の VM と異なることを意味する。多層防御においては「最も弱い VM がシステム全体の実効的なセキュリティレベルを決める」傾向があるため、攻撃面の質が VM ごとに異なる非対称な構成は、評価・監査のコストを高める。全 VM を OpenBSD にすることで、各 VM が同水準のベースライン特性を持つことを保証し、この非対称性を避けている。

## 3. 結論

- ハイパーバイザーに `vmd` を選んだのは、QEMU/KVM・Xen が前提とする「ホストは Linux/専用 Dom0」という制約と衝突せず、デバイスエミュレーション面が最小であり、ホスト OS のパッチ供給網・運用 IF とシームレスに統合されるためである。ライブマイグレーション等の欠如は、本システムの単一ホスト固定構成では実害がないと判断した上での許容済みトレードオフである。
- ゲスト OS をすべて OpenBSD に統一したのは、`vmd` の制約ではなく意図的選択である。ビルド・実行環境の ABI 完全一致によるロックステップ運用の実現、運用者が把握すべきセキュリティモデルの単一化、そして全 VM が同水準のセキュアバイデフォルト特性を持つことによる多層防御の非対称性回避が理由である。

## 4. 見直し条件

以下のいずれかが要件化した場合、本書の選定根拠を再評価すること。

- GPU を用いた推論・ハードウェアアクセラレーションが必要になった場合(`vmd` は GPU パススルー非対応)
- 複数物理ホストへのスケールアウト、または無停止メンテナンスのためのライブマイグレーションが必要になった場合
- GHC 以外の言語・ランタイムで、特定 OS への依存が強いツールチェインを採用する必要が生じた場合
